# P5 immutable release tooling

`scripts/release/build.ts` requires an independent clean committed Git source, matching source-commit test evidence, lock/upstream lock hashes, tool/native identities, compatibility schema identifiers, and asset/backend hashes. It creates a temporary candidate and renames only a verified artifact. Dirty, untracked, or mismatched evidence is rejected. Clean Git is not privacy/license clearance.

`activate.ts` only performs frontend-compatible activation in a caller-owned deployment root. Backend/native/schema changes are distinct deployment types and cannot use static activation. Activation requires validated asset hashes, matching backend/native/storage/protocol identities and a successful caller-provided candidate health check. A filesystem exclusive lock serializes activation. A failed candidate leaves the active pointer unchanged. `rollback.ts` applies the same compatibility/health validation to the prior immutable release.

`server/static.ts` defaults to the existing dist path unless an explicit release root is configured. Release pointers and artifacts are validated. Prior hashed assets are retained for lazy imports from an already-open client. Missing JS/CSS/assets return 404, not an HTML shell. Path traversal and symlink escapes are rejected. PWA shell files revalidate; retaining assets does not guarantee browser-local storage backup.

Local fixtures verify A → rejected B keeps A, successful B activation, rollback to A, old-client lazy asset responses, missing JS/CSS errors, corrupt/symlink/traversal rejection and separate schema deployment refusal. The isolated native regression verifies terminal identity and shell PID survival across these static pointer operations. Its storage fixture proves server-side noninterference only: real browser v1/v2/v3 migration and workspace restoration are exercised by P3, not claimed as a server backup.
